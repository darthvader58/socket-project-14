1 · Architecture and registration

The manager maintains peer metadata and lifecycle state. Each peer uses one UDP socket for manager messages and one UDP socket for peer messages. Multiple peer processes may share a host when their ports are unique.

Message envelope. All messages are compact UTF-8 JSON datagrams. Requests contain type, unique request_id, sender, and a payload object. Responses echo request_id and include status and payload.

Registration message format

{"type":"REGISTER","request_id":"UUID","sender":"PeerA",
 "payload":{"ip":"10.10.1.1","m_port":8001,"p_port":8002}}
{"type":"REGISTER_RESPONSE","request_id":"UUID","status":"SUCCESS","payload":{}}

The manager validates an alphabetic peer name of at most 15 characters, unique name, numeric ports in the configured group range, distinct local manager/peer ports, and no port collision for peers sharing an IP. On success it stores the peer as Free. The peer then binds its peer-to-peer UDP socket.

Time-space diagram · register

Time ↓Peer processManagerLocal effect
1REGISTER(name, IP, m-port, p-port) →Receive UDP datagram
2Validate uniqueness, name, and ports; store peer state as FreeManager state updated
3← REGISTER_RESPONSE(SUCCESS / FAILURE)Send correlated response
4On SUCCESS, bind p-port and start peer listenerPeer is ready for ring messages

All three peers registered successfully in the CloudLab run. The manager log shows PeerC, PeerB, and PeerA each received SUCCESS.

Data structures

  • Manager peer dictionary keyed by peer name, with IP, ports, and state.
  • Ordered member list returned at setup; each peer's right neighbor is member (id + 1) mod n.
  • Each peer's local table maps hash position to a nested event-ID/record mapping to handle collisions.
  • Per-peer queues correlate STORE acknowledgments and completion of count collection.
CSE 434 DHT milestone · Group 142

2 · DHT setup and ring construction

setup-dht message format

{"type":"SETUP_DHT","request_id":"UUID","sender":"PeerA",
 "payload":{"size":3,"year":1950}}
{"type":"SETUP_DHT_RESPONSE","request_id":"UUID","status":"SUCCESS",
 "payload":{"year":1950,"members":[
  {"name":"PeerA","ip":"10.10.1.1","p_port":8002},
  {"name":"PeerC","ip":"10.10.1.2","p_port":8004},
  {"name":"PeerB","ip":"10.10.1.2","p_port":8006}]}}

The manager rejects an invalid size, unregistered leader, too few Free peers, or an already active DHT. It selects two Free peers at random, marks the leader Leader and the others InDHT, and returns the leader's tuple first. IDs follow this returned order; PeerA is ID 0.

Time-space diagram · setup and ID assignment

Time ↓Leader (ID 0)ManagerPeer 1Peer 2
1SETUP_DHT(size=3, year=1950) →Validate leader/size/free peers
2← SUCCESS + ordered member tuplesChoose 2 Free peers; set Leader/InDHT states
3Set ID 0; ring_size=3; calculate right neighbor
4SET_ID(id=1, ring_size=3, members) ─────────────→Store ID 1 and right neighbor
5SET_ID(id=2, ring_size=3, members) ─────────────────────────→Store ID 2 and right neighbor

Build messages

STORE carries target ID, position, hop count, full record, and leader address. A non-target peer increments the hop count and forwards STORE to its right neighbor. The target stores the record and sends STORE_ACK to the leader. The leader sends a record directly to its right neighbor, never directly to the target node.

{"type":"STORE","request_id":"UUID","sender":"PeerA",
 "payload":{"target_id":2,"position":317,"hop_count":0,
  "record":{"event_id":"...","state":"..."},
  "leader":{"ip":"10.10.1.1","p_port":8002}}}

The leader stores ID-0 records locally and transfers other records one at a time, waiting for an acknowledgment. After data transfer it initiates a COUNT message around the ring.

CSE 434 DHT milestone · Group 143

3 · Data distribution and completion

Hashing

For ℓ records, choose table size s as the first prime larger than 2ℓ. For each record, pos = event_id mod s and id = pos mod n. This run has ℓ = 223, so the first prime above 446 is s = 449. The destination peer ID is 0, 1, or 2.

COUNT exchange. A COUNT message carries a map of ring ID to local record count and a hop counter. Each peer appends its count and forwards to its right neighbor. On its return, the leader adds its local count, prints the complete map, verifies the total equals 223, then sends DHT_COMPLETE to the manager.

Time-space diagram · count and completion

Time ↓Leader (0)Peer 1Peer 2Manager
1COUNT(counts={}) →
2Add own count; forward COUNT →
3Add own count; forward COUNT →
4Receive return; add ID-0 count; verify sum=223
5DHT_COMPLETE(peer-name) ─────────────────────────────→Accept only current leader; mark DHT Ready
6← DHT_COMPLETE_RESPONSE(SUCCESS)Log counts and successful completion

dht-complete format

{"type":"DHT_COMPLETE","request_id":"UUID","sender":"PeerA",
 "payload":{"counts":{"0":72,"1":75,"2":76}}}

The manager accepts this only from the current leader during construction, changes its phase to Ready, logs the counts, and replies SUCCESS.

4 · Implementation, test evidence, and submission notes

Implementation choices

  • Python 3 standard library: socket UDP, threading, queue, json, and csv.
  • Manager is an always-on UDP service. Peer command input is read from stdin; peer and manager messages are correlated by UUID request IDs.
  • Ports are unique per process. Group 14 uses the range 8000-8499; this run used 8000-8006.
  • Scope is restricted to the September milestone. Graceful termination and October features are not claimed.
